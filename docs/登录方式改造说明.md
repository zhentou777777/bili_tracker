# 登录方式改造说明（扫码登录 + 同设备跳转 B 站 App 确认）

> 面向不使用技术的读者。看不懂代码也能照着做，第八节是给你的「验证清单」。
> 技术细节与决策理由在 `交接文档.md` 的「阶段 E」；本文只讲「改了什么、为什么、怎么验、怎么退」。

---

## 一、一页速览

**改了什么**

登录页从「内嵌一个网页让用户在里面登录」换成了 **扫码登录 + 一键跳到 B 站 App 点确认**。

**为什么改**

原来那种做法要在一个小窗口里加载 B 站完整的登录网页，那是个很重的页面，经常白屏或者按钮点不动 —— 同类第三方客户端也有一样的抱怨。**不是我们写错了，是这条路本身就不稳。**

**现在怎么用（两种场景，任选一种）**

| 场景 | 操作 |
|---|---|
| **就用这台手机**（最常见） | 打开登录页 → 点「在 B 站 App 中确认」→ 手机会跳到 B 站 App 的授权页 → 在 B 站 App 里点「确认」→ 自动回来，已登录 |
| **手边有另一台设备** | 打开登录页 → 用另一台设备上的 B 站 App 扫屏幕上的二维码 → 在本机点确认 |

**你需要做什么**

1. 双击 `REBUILD.bat` 重新出包（**必须**：这次新增了一个依赖，旧包不含本次改动）；
2. 双击 `CHECK.bat` 看静态检查与测试是否全绿；
3. 装新包，按第八节清单在真机上试一遍登录。

## 二、原来的登录方式为什么不可靠

旧实现是：App 内嵌一个浏览器窗口，加载 `passport.bilibili.com/h5-app/passport/login`，
用户在这个窗口里自己完成扫码 / 短信 / 密码登录，然后我们从浏览器的 Cookie 里把登录凭据取回来。

问题：

- **白屏**：那个登录页是重前端页面，在内嵌窗口里很容易加载不出来；
- **控件点不动 / 样式错乱**：内嵌窗口与系统浏览器的渲染差异导致的，页面上按钮位置甚至可能点不到；
- **链路长**：要等页面加载、等用户操作、再轮询取 Cookie，每一步都可能出问题。

这套逻辑**没有删除**，它现在叫「网页登录」，是登录页右上角的备用入口（万一扫码路线出问题，还有一条路能走）。

## 三、新方式：一句话讲清原理

B 站的扫码登录，官方流程本来就是三步：

1. **申请一张二维码**：向 B 站要一个 32 位的临时钥匙（`qrcode_key`），和一条对应的链接；
2. **等确认**：每 2 秒问一次 B 站「这张码有人确认了吗」；
3. **取凭据**：一旦确认，B 站会在那一刻把登录凭据（Cookie）发给我们。

关键是**第 1 步拿到的那条链接**：

```
https://account.bilibili.com/h5/account-h5/auth/scan-web?qrcode_key=xxxxx
```

它看起来是给「扫码」用的，但它其实是 **B 站自己的「授权页」**。
手机上装了 B 站 App 之后，用系统打开这条链接，**手机会自动把它交给 B 站 App**（这是安卓/iOS 的
「应用链接」机制，B 站官方注册过这个地址），于是就直接进到 B 站 App 的「确认授权」界面 ——
用户点一下「确认」，我们这边的第 2 步立刻就会收到「已确认」，登录完成。

**所以「跳转 App 授权登录」不是什么黑科技，它就是「把 B 站自己的授权页交给系统打开」。**
这也是登录页上那个按钮「在 B 站 App 中确认」做的事。

## 四、必须说清楚的一件事：BBPlayer 并没有「跳转 App 授权登录」

你让我参考的 [BBPlayer](https://github.com/bbplayer-app/BBPlayer)（一个用 React Native 做的 B 站音乐播放器），
我把它登录相关的源码都读了一遍。它的登录方式实际上是**三种**：

1. 扫码登录（`qrcode-login.tsx`）
2. 手机号短信登录（需要过极验图形验证，`usePhoneLogin.ts`）
3. 手动粘贴 Cookie（`CookieLoginModal.tsx`）

**它没有官方授权登录，也没有「跳转 App 授权」这个独立功能。**

但它做了一件很聪明的事，就在扫码页里：

```tsx
// 二维码下方那个按钮
<Button onPress={handleOpenLink}>在 Bilibili 客户端打开</Button>

// 页面底部的提示原文
请使用 Bilibili 客户端扫描上方二维码。
若处于同一台设备，可点击按钮直接跳转 B 站进行确认。
```

`handleOpenLink` 做的事只有一件：**把二维码那条链接交给系统浏览器打开**。
这正是第三节讲的原理 —— 于是「同一台设备」也能完成登录，不需要第二台手机来扫。

**我们这次学的就是这套**：界面结构、状态提示、过期遮罩、跳转按钮，都参照它；
但配色沿用本项目自己的深色主题，没有照搬它的 Material 3 浅色/深色两套皮肤。

## 五、另一种可能：B 站官方的「跳转 App 授权登录」

B 站**确实有**官方的跳转 App 授权登录（OAuth 2.0），而且完全符合你描述的样子：集成官方 SDK →
调用授权 → 跳到 B 站 App → 弹出授权页 → 用户同意 → 回调返回授权码 → 用它换访问令牌。

**但它对本项目不可用**，两个原因，缺一不可：

**1. 申请门槛：不开放给个人。** 官方入驻要求提交营业执照、加盖公章的公函等企业材料，
文档里明确写着「暂未开通个人开发者的申请入驻」，审核还要 2–3 个工作日。这是面向企业和机构的通道。

**2. 更致命的：拿到了也用不了。** 授权只能换取 `access_token`，而它能调用的接口仅限于
「你申请并通过审核的 scope」（通常是读用户昵称、头像这类基本信息）。
它**换不到 SESSDATA**——而 SESSDATA 才是调用本项目需要的那批接口的凭证：
关注列表、空间动态、观看历史。没有 SESSDATA，登录成功也拿不到任何一条动态。

**结论：官方授权登录不是「麻烦一点」，而是「就算做了也达不到目的」。** 所以本项目走的是第三节那条路。

## 六、登录成功后，我们存了什么

只存这几个必要字段（加上设备指纹类），全部写入**本机 Keystore / Keychain**：

| 字段 | 作用 |
|---|---|
| `SESSDATA` | 登录态本体。它是 **HttpOnly**，所以在网页里用脚本也读不到 —— 这也是「只能靠接口下发、不能靠网页抓取」的原因 |
| `bili_jct` | 写操作（收藏、点赞等）需要的校验令牌 |
| `DedeUserID` | 当前账号的 UID，用来读「我的关注列表」 |
| `buvid3` / `buvid4` 等 | 设备指纹。**缺了会被 B 站判为异常并拒绝服务**，所以一并保留 |

这些内容**不会离开这台设备**，不会上传到任何服务器。

## 七、三个坑（诚实记录）

### 7.1 最坑的一个：外层 `code` 恒为 0

B 站轮询接口的返回长这样：

```json
{ "code": 0, "message": "OK",
  "data": { "code": 86101, "message": "未扫码" } }
```

**外层的 `code: 0` 只表示「HTTP 层请求成功」，跟「有没有人扫码」毫无关系。**
真正的扫码状态在 `data.code` 里：

| `data.code` | 含义 |
|---|---|
| `86101` | 还没人扫 |
| `86090` | 已扫码，等 App 里点确认 |
| `86038` | 二维码过期（有效期 180 秒） |
| `0` | 已确认，凭据此时才下发 |

只看外层 `code` 的话，第一次轮询就会判定「登录成功」，然后发现 Cookie 是空的。
本项目的做法：状态码与解析路径都写在规则文件里，代码只读规则，不写死数字（见 7.3）。

### 7.2 第二个坑：成功后的回调链接不是「带 Cookie 的链接」

确认成功时返回的 `data.url` 是一条跨域回调地址。它有两个必须同时满足的条件，缺一个就拿到空 Cookie：

1. **必须带 `Referer: https://www.bilibili.com/`** —— 不带的话，服务器返回一个
   **没有任何 Cookie 的空跳转**，请求看起来完全正常；
2. **必须禁止自动跟随跳转** —— 凭据挂在**第一跳**的响应头上，自动跟随会把这一跳的信息静默丢掉。

两个坑叠加起来的症状是：「扫码成功 → 取凭据 → 凭据是空的」，而且网络层一切正常，极难排查。
本项目两条路都做了：优先用轮询响应自带的凭据，不够再走回调补齐。

### 7.3 关于「规则文件」

本项目的一贯做法是：接口地址、参数、解析路径都写在 `assets/rules/platforms.json` 里，
接口一变改 JSON 就行，不用重新发版。这次登录接口也照这个规矩外置了（`login` 段）。

顺带修了一个会导致「改了规则却不生效」的老问题：规则缓存的版本号比内置文件高时，会压住新规则。
现在改为**取版本更高的那一份** —— 否则这次把规则版本从 4 提到 5 也可能被旧缓存挡住。

## 八、真机验证清单（请逐条确认）

在装了新包的手机上依次试：

1. 打开登录页，**二维码是否正常显示**（白底黑码，不是空白/纯黑方块）；
2. 状态文字是否为「等待扫码」（不是一上来就说成功）；
3. 点「在 B 站 App 中确认」→ **是否真的跳到了 B 站 App**；
   - 若没跳：应弹出提示「链接已复制到剪贴板」，此时把链接粘到浏览器打开，也应看到授权页；
4. 在 B 站 App 里点「确认」→ 回到本 App，**状态是否变成「登录成功」并自动返回**；
5. 返回后打开「UP 主」页，**关注列表能刷出来**（这一步才真正证明凭据可用）；
6. 等 3 分钟以上不操作，**二维码是否变成「已过期」并出现「重新生成」按钮**；
7. 点右上角「网页登录」，**备用入口是否还能打开**（老用户惯用路径不被破坏）；
8. 设置页「退出账号」后再登录一次，**流程是否可重复**；
9. 全程**不应出现闪退**。

> 第 3、4 条如果失败，请把屏幕提示原文告诉我 —— 那基本能直接定位到是「App Links 没接管」
> 还是「凭据解析出错」，这两类的修法完全不同。

## 九、如需回退

本次改动集中在一个提交里，整体回退：

```bat
git log --oneline -5               :: 找到「阶段 E」那次提交号
git revert <提交号>                 :: 生成反向提交，代码回到本次改动前
```

只回退某一个文件：

```bat
git diff HEAD~1 -- lib/ui/login_page.dart
git checkout HEAD~1 -- lib/ui/login_page.dart
```

回退后请注意两件事：

- `assets/rules/platforms.json` 的 `version` 会回到 4，**旧缓存可能压住规则**，
  保险做法是先在设置页清一次本地数据再登录；
- `pubspec.yaml` 里的二维码依赖会一起回退，**需要重跑一次 `REBUILD.bat`**。
